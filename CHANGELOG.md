### Fixes
- **Patient list search race and error handling** (`PatientListViewModel`): a slower earlier search could overwrite the newest result, and a failure left the screen stuck loading. Only the latest request now publishes; failures reset the flags. Two regression tests (both verified failing before the fix). Commit `613d399`.
- **Diagnostics export off the main thread** (`MainActivity`): log read + AES zip no longer run inside `runBlocking` on the UI thread. Commit `ceee5d3`.
- **Sync-info worker** (`SyncInfoDatabaseWriterWorker`): cancel the `shareIn` scope in `finally`, rethrow `CancellationException`, log with Timber instead of `println`. Commit `159113c`.

### Removed (dead code)
- 11 unreferenced RecyclerView adapter/view-holder files and the `activity_login`, `activity_basic_login`, `activity_splash` layouts. Verified by compiling main + unit-test + androidTest sources and assembling the debug app. Commit `8795853`.

### Features and fixes added after the patient-list decision
- **A13 fixed** (`f305227`): at least one patient list must be selected; the sync never downloads patients unscoped. Verified on device.
- **A14 fixed** (`fab0b4a`): login no longer sends two `Authorization` headers when credentials are stored (400 → 200). Verified on device.
- **Search by identifier or phone** (`3750098`, hint text `85ec694`): verified on device.
- **Unsaved-changes guard** on registration/edit: first version (`9e474a4`, `82f9698`) **broke registration** (see below); rewritten in `2673803` to be tap-based and to never read the questionnaire response. Verified on device.
- **Regression found and fixed (`2673803`):** the first guard read the questionnaire response early, which made the form library drop conditional items and later answers; patients were saved without gender and rejected by the server (422). Caught by the offline-create → upload test, **not** by the unit or instrumentation suites. Offline create → upload now verified end to end (patient uploaded, identifier assigned).
- **UI reuse** (`3927482`): shared inset helper, `composeView {}` fragment hosting, Home card table. 51/51 instrumentation tests that pass at baseline still pass.
- Tests: 18 → 40 unit tests (sync URL helpers, patient-list scoping, auth header, answer signature, unsynced scan characterization).

### Tried and rejected (measured)
- Running the unsynced-resources local-change lookups concurrently: 37–46 s vs ≈31 s sequential. Reverted. Timing instrumentation showed the cost is `search<Observation>` (26 s), not the lookups (3.6 s).

### Audit corrections

- C1 not batchable via the public `FhirEngine` API; C2 negligible on this backend (no `RiskAssessment` resource).

## Dependencies, settings and UI (branch `chore/upgrade-dependencies`)

- **Stable Open Health Stack**: FHIR engine 1.2.0 and data-capture 1.3.1 from Google Maven; the GitHub Packages repository and token are gone. AndroidX, coroutines, Retrofit, Moshi, Dagger, Room and Mockito are on current stable versions. The Compose BOM stays at 2024.12.01, the generation data-capture 1.3.1 is built against: a newer BOM crashed forms on the second page (PEDS: `layout state is not idle before measure starts`).
- **Audit trail and a better "Send diagnostics"**: a light audit log for the support team (`audit/AuditLog`). It records high-level steps as one JSON object per line (UTC time, session, sequence, action, outcome, user, short details): app start and crashes, login (method `basic` / `sso` / offline biometric or device credential, user, failures with the reason), logout, guest session, sync started/completed/failed, location and patient-list choices, patient opened / created / edited, encounter created / edited, group session started / submitted, settings changed, forms fetched, data exported / imported, unsynced data deleted, diagnostics sent. Details are identifiers and counts only (patient resource id, form id) - never names, answers, passwords or tokens. It keeps the last `max-actions` entries (`<audit max-actions="500"/>` in `app_config.xml`, 50-5000; older ones are overwritten, the file is compacted only after growing by a fifth); writing is queued to one low-priority thread, each line AES-encrypted like the application log, and it survives logout. **Send diagnostics** now opens a dialog with a checkbox per part, all ticked by default: application logs, audit trail, sync information, unsynced resources in full (one resource per line, streamed, flagged as containing patient data) and, new, device and app information (version, device, storage, memory, network, settings, form counts, build configuration without secrets, recent process exits). The report is built on a background thread of low priority, piece by piece into files, into the same AES-256 archive (`DiagnosticsBuilder`). Verified on the emulator: dialog, report contents (decrypted with the configured password), the audit lines for start / patient created / opened / unsynced deleted / diagnostics sent; ring-buffer compaction was reasoned, not exercised.
- **Settings: fetching forms from the server, favorites in "Forms"**: the fetch action was hidden whenever the user was in a guest session ("Continue without signing in"), so it looked like it did not exist. It is now always listed while "Use embedded forms only" is off, disabled with "Sign in to check the server for new and updated forms" when it cannot work, and pressing it also switches the toggle off (the server's forms are then wanted). It now brings new forms *and* newer versions of the ones the device holds (compared by `meta.lastUpdated`, or the version label), not only forms the device lacked; the result says how many were added and updated. "Favorite forms" moved into the "Forms" section too. Verified on the emulator against the test server (read only): guest view (disabled with the reason), signed-in view, fetch answered "up to date" since the device already held the server's 26 questionnaires; adding or updating a form was not exercised because there was nothing new on the server.
- **Settings: one "Forms" section and "Use embedded forms only"**: the "Form sections" card and the "Forms" card (fetch questionnaires) are now one "Forms" section, with everything they had (sections editor, reset, fetch). New toggle "Use embedded forms only", on by default and applied on Save (`EmbeddedFormsStore`): the sync no longer downloads `Questionnaire` resources (`SyncUrls`), forms the engine already holds from the server are ignored (every loader goes through `storedQuestionnaires` / the embedded fallback), the form lists show only the forms shipped with the app, and the "Fetch questionnaires" action is hidden (and refuses to run). Turn it off to get the previous behaviour. Verified on the emulator: the new section, the toggle on, and the group form list from the embedded forms; the fetch action and a real sync with the toggle off were not exercised (guest mode, server not used).
- **Color-blind palette** (Settings > Appearance > Color vision): a second palette for users with red-green or blue-yellow color blindness, in light and dark. It follows Okabe-Ito: blue carries what green carries in the standard palette (done, online, progress) and a dark vermillion/orange carries what red carries (errors, offline, missing answers), amber is the warning, and the neighbouring states differ in lightness too, with slightly stronger text and outline contrast. States already come with an icon or a word, never the hue alone. It applies to the Compose screens (`OpenMrsTheme`), to the XML screens and to the data-capture forms through a theme overlay (`ThemeOverlay.OpenMrs.ColorBlind`, added to each activity by `ColorVisionStore`). The chips show the three status colors of each palette; it is applied on Save and the screen is recreated. Verified on the emulator: settings, home, registration form and review page in light and dark.
- **Group session: colours and switching patients**: the patient tabs and the page progress line used fixed light colours (light cyan/grey pills, black text, a lavender track with a stray dot, a Google-blue spinner), which clashed with the app and were unreadable in dark mode. They now come from the app theme (selected tab = primary container, others = surface variant, no extra indicator line under the tabs; the form's progress line is a plain primary bar on a neutral track; the loading spinners use the primary colour). Switching patient no longer waits for the draft to be written or validates twice, validation runs off the main thread, and the forms of the last three patients stay alive (hidden) so going back to one is instant with its answers and page as left; a changed questionnaire or a restored draft rebuilds them. Verified on the emulator: tab switches went from ~30 skipped frames (99th percentile frame 600 ms) to none (about 200 ms), answers kept across switches, draft resume, incomplete-form dialog.
- **Registering a patient**: the registration form could not be saved because the copy of it on the server (and so the one synced to the devices) carries the app's compact aliases (`@h/questionnaire-itemControl`, ...) in its extension urls and has lost its translations. The form library does not know the aliases, so gender was a dropdown, the months question always showed and was required, nothing was hidden or limited. A questionnaire with aliases is now replaced by the bundled version of the same questionnaire (one the app does not ship gets its aliases expanded); this holds for every form (create, edit, lists). The age rules were also fixed: no pre-filled `0 years / 0 months` (a patient was a newborn when nobody typed an age), years 0-120, months 0-11 only for under 6, a birth date in the future is refused with its own message, and registering and editing use one rule for the birth date. Only the current language is sent to the form library; the registration form is parsed in the background after launch; the HTTP logger no longer writes response bodies (patient data) to the app log. Verified on the emulator: known date, estimated age 30 years, 3 years 5 months, 1 year 2 months, future date, 130 years, 12 months, missing age and gender, then editing a patient.
- **Import / Export** (Home card and a link on the Sync screen): when a device cannot sync, *Export* writes every resource with changes not yet uploaded (new patients, encounters, observations, edits) into one `.omrs` file after asking for a 4-digit PIN (typed twice), to share or save; on another device *Import* asks for the PIN, stores the items as local changes, and *Upload now* syncs them like anything entered there. The file is a gzip-compressed FHIR `Bundle` sealed with AES-256-GCM, the key derived from the PIN with PBKDF2 (60,000 rounds, random salt), so a wrong PIN or a damaged file is detected and nothing readable is in the file. A 4-digit PIN is only 10,000 combinations: it keeps the data from being casually read in a mail or chat, it is not strong protection. It is light: the pending changes are listed with one query on the engine's change table (the engine API is the fallback), resources are read by id, nothing is held beyond the one file. Edits of records the receiving device has not downloaded, and files imported twice, are skipped and counted. Verified on the emulator: wrong PIN refused, right PIN imports, export re-read and decrypted outside the app.
- **One look for messages**: "Sync Completed" was a plain grey snackbar while everything else was a system toast. All of them (about 40 toasts and 9 snackbars) now go through one `AppMessage`: a rounded card like the sync popup, with a green check, red alert or teal info icon, sliding in above the bottom bars and fading by itself or on tap. Used inside the patient-selection dialog too. The two biometric-setup notices in `AuthDialogs` stay system toasts, because the app switches screen right after showing them.
- **Sync that never finished**: the download crashed (`NullPointerException`) whenever a downloaded resource had no `meta.lastUpdated`, which dropped the page and ended the sync as failed with no message while the progress bar sat at 100%. The newest-timestamp step now skips resources without one. The progress was also misleading: the total the sync library gives (e.g. 28) only counts the matching patients, while the download also brings their encounters and observations (914), so the bar pinned at 100%; it now becomes indeterminate with a live "N items synced so far" count (popup, pill, Sync screen, notification, history of a running sync). A session left open by a sync that was cut short is closed as interrupted when the next one starts, so its numbers no longer carry over. Verified on the emulator: a sync that failed after 914 items now completes (940/940 in 48 s).
- **Form check on the emulator** (fresh install, UI-driven, basic auth): each form that is selectable in the picker (22) was created with the first and with the last answer of every question (dropdown options picked from the list, show/hide rules and required fields followed) and submitted; all 22 submit without a crash. Edit mode was run for each of them (open an existing encounter, answers come back filled in, change every answer, submit, reopen). The four forms with `observation-child` groups (Closure, Assessment, Follow-up, Activity) keep consistent parent links after editing. WHODAS 2.0, Brief Cope and the second DASS-21 are bundled but not listed in the sections of `app_config.xml`, so they are not selectable until a section lists them. The project test suites were not run.
- **Settings**: one file per app, `res/xml/app_config.xml`, replaces `local.properties` settings, the generated resources and the per-module `server.xml` / `auth_config.xml` (see README, *Configuration*). Sync URLs, SSO endpoints and the constants nobody changed are no longer settings; form sections are declared with XML tags.
- **Look and feel**: OpenMRS 3 teal/Carbon palette (light and dark) for Compose, XML and the data-capture form; bottom navigation (Home / Patients / Group / Sync); Home status header; avatar patient rows; one rounded search field.
- **Top bar no longer covers content**: main and login activities are edge-to-edge on every API level and screens pad by the measured app-bar height (before, only API 35+ was right). The content also clears the navigation bar and keyboard.
- **Data capture**: `newQuestionnaireFragment` / `onQuestionnaireResult` replace five copies of the builder and result wiring; registration loads each identifier type once.
- **Bug fixed**: the bottom-bar "Group" tab crashed (wrong navigation argument keys, `patientId` / `isGroupEncounter` instead of `patient_id` / `is_group_encounter`); it now builds the arguments with the generated `CreateEncountersFragmentArgs`.
- **Verification note**: the UI, edge-to-edge and data-capture changes were checked by building, installing on the emulator and looking at the screens (home, patient list, settings, registration, group session flow). The automated suites were **not** re-run after these changes, at the owner's request; run them before merging.
- **Patient lists**: the patient list and the group-session picker only show members of the selected patient lists (taken from the Group resources on the device). Patients registered on the device stay visible until uploaded; with no list selected, or lists not downloaded yet, nothing is hidden. Not exercised on the emulator because its config downloads no Group resources.
- **Bundled questionnaires**: `core/src/main/assets/questionnaires/<id>.json` holds the 26 questionnaires published by the test backend (read-only download). Settings has **Fetch more questionnaires**: it lists the server's questionnaires, compares ids with the engine and the bundled files, and stores only the missing ones (as a download, so nothing is queued for upload). Verified on the emulator: "Questionnaires are up to date."
- **No list, no patient data**: patient requests are scoped to the selected lists whatever the configured sync URLs look like. A `Patient` URL without the `_has:Group:member:id=` placeholder (as in a plain `fhir_sync_urls`) used to download every patient; the filter is now added automatically, and with no list selected all patient-data requests (Patient, Encounter, Observation, ...) are skipped, also in the first-time sync. Verified on the emulator: submit with no list leaves 12 locations and 26 questionnaires, no patients.
- **Patient lists by location**: the group location is read from the string extension the server publishes (it only accepted a reference before), so lists show up for their location when `filter_patient_lists_by_group=true`; the list screen has a "Change location" action.
- **Offline login answer is remembered**: after login the opt-in dialog is shown only until the user has answered it ("enable" or "not now"); the answer survives later logins. Settings > Security shows the state and **Reset offline login** removes the saved offline login and the answer so the next login asks again. If the password changes, reset it so the saved offline credential is refreshed.
- **Light / dark / system** (Settings > Appearance): saved on Save, applied at startup to the XML and Compose screens.
